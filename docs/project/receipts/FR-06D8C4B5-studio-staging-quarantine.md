# FR-06D8C4B5 — Studio retained staging quarantine

This source-only capability is the bounded containment step after the accepted C4B1 writer boundary, C4B2 runtime/backup drain, C4B3 cleanup candidate, and C4B4 exact-inode process-reference scan. It is intentionally not cleanup, settlement, process drain, deployment, or full-host closure.

The implementation consumes the exact chained B1/B2/B3/B4 receipts, requires the same maintenance operation/generation and the same boot as the B4 process scan, and reopens only the retained candidate path through the existing no-follow directory-descriptor boundary.

On the mutation path, before mutating the Studio namespace, the implementation revalidates the retained staging/final inode layout, performs two candidate-specific /proc scans, and obtains fresh Docker inventory twice: once at stage entry and once at the last safe point immediately before the rename. After the rename it obtains two additional fresh Docker inventories around two more /proc scans, for four fresh inventories total. On a same-boot recovery path there is no new rename and no new pre-rename claim; it obtains three fresh inventories: at entry, after exact quarantine recovery is established, and again before receipt issuance. Each inventory rechecks the current backend/studio-worker writer epoch plus the backup-worker container identity and complete read-only mount evidence.

The only Studio namespace mutation is a same-directory Linux renameat2(RENAME_NOREPLACE) from the owned staging name to the deterministic name `.studio-quarantine-<candidate_sha256>.retained`. No overwrite-capable fallback is permitted. The inode is retained, any owned final hardlink is preserved, the directory is fsynced, and the source is held by an O_NOFOLLOW descriptor through the atomic move.

A same-boot rerun can recover a move that completed before receipt persistence only when the deterministic quarantine entry is the exact retained candidate inode and the original staging name is absent. Both names present, a foreign quarantine inode, final-layout drift, current-container drift, ambiguous /proc evidence, any visible reference, rename failure, or malformed/unavailable Docker inventory block the receipt. A post-rename failure leaves the retained quarantine inode in place so a later same-boot run can revalidate it rather than deleting bytes.

A successful receipt explicitly keeps process_drain_verified=false, cleanup_authorized=false, settlement_authorized=false, quarantine_deletion_permitted=false, final_deletion_permitted=false, and full_host_closure=false. No kill/stop/restart, database/admission mutation, unlink/remove, final-file deletion, execution settlement, retry, production migration, or live production mutation is part of this source acceptance. Root execution and the pre-existing private state-root are now preflighted before any Studio namespace mutation; the state-root is validated again at receipt persistence.
